# ColdStart 产品与系统架构规格

- 日期：2026-10-30
- 产品名：ColdStart / 冷启动
- 仓库：`huangqcEvent/coldstart`
- 状态：已确认架构；阶段 1-18 已实现，后续边界见各阶段独立设计
- 文档范围：产品边界、系统架构、领域模型、MCP 协议、安全规则和 MVP 验收标准

## 1. 背景与目标

ColdStart 服务于“Vibe Coding 之前的阶段”。目标不是生成另一份超长 Prompt，而是把项目从一句想法推进到可被 Agent 稳定执行的状态：

1. 整理需求、角色、模块、流程、技术栈和平台范围。
2. 识别账号、凭据、备案、证书、提审和上架等前置条件。
3. 生成带依赖、验收标准、人工门禁和外部等待时间的开发计划。
4. 通过 MCP 将当前任务所需的最小上下文交给 Codex 等外部 Agent。
5. 接收结构化完成报告，推进计划并保留证据与审计。
6. 只把缺失信息、业务决策、授权、审批和不可逆操作交给人工。

ColdStart 不生成业务代码，不自动启动 Agent，不替代 App 商店或小程序平台的人工发布流程。

## 2. 产品边界

### 2.1 目标项目

- Web 应用
- 服务端与应用接口
- 管理后台
- iOS/Android App
- 微信等小程序

一个项目可以关联多个代码仓库；一个仓库也可以承载多个平台目标。项目不为其他行业或硬件领域提供通用模板。

### 2.2 目标用户与运行方式

- 单用户、单机桌面客户端。
- 第一版以 Windows 为主，核心模块不绑定 Windows API。
- 无多租户、云端协作、团队权限和远程任务执行。
- Codex 主动通过 MCP 拉取任务，ColdStart 不主动启动 Codex。

### 2.3 明确不做

- 不运行 Agent 本身，也不接受 Agent 自报的完成结果；ColdStart 会独立执行仓库配置的本地验证命令。
- 不自动合并受保护分支、不自动部署生产环境。
- 不自动完成 App Store、应用商店或小程序提审。
- 不提供通用 CI/CD、云构建或线上监控平台。
- 不做浏览器 DOM 自动化创建 GitHub 仓库；产品使用官方 OAuth 和 API。
- 不承诺抵御拥有当前用户 Shell 权限的恶意本地进程。

## 3. 已确认的关键决策

- 产品名使用 ColdStart，中文名“冷启动”。
- 使用 Tauri 2、Rust、React、TypeScript 和 SQLite；Rust 负责全部领域与本地能力，前端只负责交互界面。
- Codex 通过 MCP stdio 主动领取任务。
- 每个任务只返回按需编译的上下文，不返回完整项目资料。
- 报告始终使用 `agent_report` 结构；阶段 7 起，Agent 编码任务还必须通过仓库级本地命令验证。
- 每个任务可配置 `agent_report` 或 `human_acceptance`；仓库级命令验证由 ColdStart 独立执行，不信任 Agent 自报的命令结果。
- 生产部署、App/小程序提审、受保护分支写入、破坏性数据库操作必须人工确认。
- GitHub 私有仓库通过 OAuth Device Flow 和 REST API 创建，不依赖浏览器页面自动化。
- 代码任务在独立任务分支完成；报告通过后自动推送任务分支。
- 任务分支推送成功后，可由桌面端人工创建 GitHub 草稿 PR；MCP 不提供 PR 写工具。
- PR 状态、Checks、Review 与行内评论只能由桌面端人工刷新；同步全部使用 GET，MCP 不提供 PR 读取或写入工具。
- PR 合并状态只作为人工验收提示展示，不构成自动合并许可；ColdStart 不调用 GitHub 合并、重跑或分支更新接口。
- 不自动合并主分支、不强制推送、不自动删除远程分支。

## 4. 人工介入模型

系统采用“按需中断”而不是固定阶段确认。以下五类事件进入统一 Inbox：

1. **补充信息**：业务规则、域名、AppID、企业资质、账号、截图、设计偏好。
2. **业务决策**：定价、角色权限、范围取舍、低置信度需求。
3. **授权**：外部账号登录、OAuth 授权、费用确认、远程仓库权限。
4. **审批**：生产发布、提审、受保护分支、破坏性操作。
5. **人工外部操作**：实名认证、商店后台操作、微信平台配置、支付商户审核。

每个信息请求包含：问题、原因、示例、可选默认值、影响范围、最晚提供时间、是否阻塞和当前状态。信息请求只阻塞其声明的任务或里程碑，不默认阻塞整个项目。

长周期事项在其结果需要之前提前出现，例如备案、软著、证书和平台审核；即使当前编码不受阻塞，也会作为风险提示进入 Inbox。

## 5. 系统架构

```text
Codex / MCP 客户端
        │ stdio
        ▼
  Rust MCP 桥接 ──────────┐
                          │
Tauri 桌面端 + WebView ───┼──> Rust 核心 crate
                          │      ├─ 蓝图编译器
Rust CLI 运行器 ──────────┘      ├─ 计划编译器
                                  ├─ 工作调度器
                                  ├─ 上下文编译器
                                  ├─ 策略 / 门禁引擎
                                  ├─ 证据校验器
                                  └─ 事件存储

基础设施适配器
  ├─ SQLite（WAL）
  ├─ 项目主目录 / 制品存储
  ├─ Git 与 GitHub 提供器
  ├─ 系统凭据库
  ├─ 本地命令运行器
  ├─ 文档导入器
  └─ OpenAI 兼容模型适配器
```

系统是一个本地模块化单体。Tauri UI、MCP Bridge 和 CLI 复用同一套 Rust 领域核心；它们不是三套独立实现。前端不直接访问数据库、文件系统、Git 或系统凭据。

## 6. 本地运行形态

- Tauri 2 负责桌面窗口、WebView 与原生命令边界；React/TypeScript 只负责界面和交互状态。
- Rust core crate 负责领域模型、用例、状态机、计划、策略和审计，不依赖 Tauri 类型。
- Codex 启动一个按需运行的 Rust MCP stdio 进程；进程退出后任务租约和状态仍保存在 SQLite。
- Rust CLI 为凭据注入和受控命令执行提供入口。
- 不使用常驻后台服务。桌面 UI 关闭时，MCP 仍可完成领取、心跳、阻塞和报告；UI 下次打开后展示状态。
- SQLite 使用 WAL，任务领取使用 `BEGIN IMMEDIATE` 保证原子性。
- 数据库迁移由独占文件锁保护；普通读写不阻塞其他进程。
- UI 通过文件监听、焦点刷新和短轮询观察 MCP 进程写入的状态。

Rust workspace 计划分为：

```text
crates/core       领域模型、用例、状态机和计划引擎
crates/storage    SQLite、迁移、事件存储和投影
crates/adapters   Git、GitHub、文档解析、模型与系统凭据
crates/mcp        MCP stdio 服务
crates/cli        本地能力运行器
apps/desktop      Tauri 2 应用
web               React + TypeScript 前端
```

SQLite 通过 `rusqlite` 访问，启用 WAL、`busy_timeout` 和显式事务；阻塞式数据库工作放在专用线程或 `spawn_blocking` 中。Git 操作调用系统 `git`，以兼容已有凭据助手、SSH 配置和 hooks。凭据使用系统 Keychain/Windows Credential Manager 适配器；HTTP 调用使用 Rust 异步客户端。前端与 Rust 之间通过 Tauri 命令和事件传递 DTO，不传递明文密钥。

## 7. 事实源

- **项目知识**：项目主目录中的 Markdown/YAML 是编辑入口；发布蓝图时生成不可变快照，任务引用内容哈希与快照版本。
- **计划结构**：不可变的 `PlanRevision` 是计划定义的事实源；Git 中的计划文件仅为只读快照。
- **运行状态**：追加式事件日志是事实源；任务状态表、看板和统计是投影。
- **代码**：各代码仓库的 Git 历史是事实源。
- **凭据**：操作系统凭据库是唯一明文存储位置。
- **项目事实**：域名、企业名称、AppID 等存于事实表并带版本；Secret 只保存 `secretRef`。

禁止让 UI、MCP 或 Agent 直接编辑同一份实时状态。所有变更经核心用例写入并产生事件。

## 8. 项目主目录与代码仓库

项目主目录（Project Home）是项目知识和本地运行数据的根目录：

```text
project-home/
  coldstart.project.json
  docs/
    requirements/
    architecture/
    decisions/
    release/
  .coldstart/
    state.db
    artifacts/
    snapshots/
```

- `coldstart.project.json` 保存项目 ID、平台目标、仓库映射和模板版本。
- `docs/` 可纳入 Git 并配置独立远程。
- `.coldstart/state.db` 和运行快照默认不进入 Git。
- 代码仓库可以在项目主目录内，也可以关联外部绝对路径。
- 每个 `Repository` 可配置多个远程，`origin` 为主远程；每个 `PlatformTarget` 指向仓库与子目录。

## 9. 领域模型

核心实体如下：

- `Project`：一个完整产品。
- `Repository`：本地 Git 仓库及其远程、分支和凭据引用。
- `PlatformTarget`：Web、服务端、管理后台、App、小程序等交付目标。
- `ArtifactRevision`：需求、架构、ADR、接口契约和发布材料的不可变版本。
- `BlueprintRevision`：需求、模块、技术决策、能力义务、风险和发布条件的结构化版本。
- `PlanRevision`：任务定义、依赖、里程碑和门禁的不可变版本。
- `TaskSpec`：计划中的任务定义，使用稳定 `taskKey`。
- `WorkItem`：任务运行实例，绑定任务契约哈希和进度。
- `WorkRun`：一次 Agent 执行，记录 Agent、分支、开始和结束时间。
- `Lease`：任务独占租约，支持心跳、续期和超时。
- `Evidence`：Commit、文件变更、命令摘要、截图、构建产物和人工说明。
- `InfoRequest` / `ProjectFact`：信息请求及最终事实值。
- `Decision`：业务或技术决策及其理由和影响。
- `Capability`：OSS、短信、支付等三方能力及环境状态。
- `ApprovalGate`：必须人工确认的高风险动作。
- `ChangeRequest`：需求变化与影响分析。
- `EventLog`：状态变化的追加式审计记录。

## 10. 蓝图结构

蓝图是带稳定 ID 的结构化对象，不是自由文本。必须包含：

- 产品目标、用户角色、术语、范围和明确不做的内容。
- 平台矩阵、模块、功能和模块依赖。
- 用户流程、页面清单、数据模型和接口契约。
- 非功能要求、权限模型、安全与合规义务。
- 技术栈选择、理由、约束和变更影响。
- 三方服务、环境、账号、资质和发布前置条件。
- 假设、风险、未决信息和来源引用。

每个需求、模块、接口、能力义务和验收标准都有稳定 ID。AI 提取内容必须保留原文档来源和内容哈希。蓝图的发布过程执行结构校验；校验失败时不能生成可执行计划。

## 11. 计划与任务模型

计划由确定性模板与 AI 建议共同生成。模板定义阶段、依赖规则和门禁；AI 负责提取和填充内容。计划发布前必须通过 DAG 校验，禁止循环依赖和缺失引用。

计划同时覆盖：

- 项目骨架、设计基线、数据模型和契约。
- 服务端、管理后台、App、小程序的纵向功能切片。
- 三方能力接入、联调和环境准备。
- 测试、发布材料、商店提审和运维准备。
- 外部长周期人工事项。

任务类型包括 `agent_coding`、`human_input`、`human_external`、`approval_gate`、`milestone`，未来可增加 `automated_check`。

每个 `TaskSpec` 包含：

- 目标、范围、明确不做和所属模块。
- 仓库、平台目标、`baseRef`、工作分支和允许修改路径。
- 前置任务、资源锁、必需信息、能力和人工门禁。
- 输入资料、接口契约和上下文引用。
- 验收标准、验收策略和证据要求。
- 完成报告 schema、关键路径标志和截止时间。

依赖分为 `blocks`、`informs`、`conflicts_with`。只有 `blocks` 影响可领取资格。任务应能在一个 Agent 会话内完成；上下文超预算或验收范围过大时必须拆分。

计划修订后，未变化的 `taskKey` 继承运行状态。契约实质变化的执行中任务保留在旧契约上，并标记 `contractState=stale`；不能静默替换任务内容。

## 12. 状态机

`WorkItem` 状态：

```text
draft -> ready -> claimed -> in_progress -> submitted -> done
               │            │                 │
               │            ├-> blocked       ├-> reopened
               │            └-> failed        └-> cancelled
               └-> cancelled
```

- `draft`：定义尚未满足可执行条件。
- `ready`：依赖、信息、能力、门禁和资源锁均满足。
- `claimed`：已生成租约，尚未开始执行。
- `in_progress`：Agent 已开始并持续心跳。
- `submitted`：收到报告，正在进行结构与证据校验，或等待人工验收。
- `done`：验收策略允许完成。
- `blocked`：存在硬阻塞，创建或关联对应请求。
- `failed`：本轮执行失败，可由人工或新运行重新开启。
- `reopened`：完成后发现回归或证据失效。
- `cancelled`：任务被显式取消。

租约超时不会把任务标记为完成：`WorkRun` 记录为 `expired`，任务回到 `ready`，并提示上一轮可能留下未提交修改。

## 13. 上下文编译器

上下文包只包含当前任务执行所需内容：

- 任务目标、范围、平台、仓库、分支和允许路径。
- 相关需求、流程、数据模型、接口和设计约束片段。
- 相关技术决策、编码规范、验收标准和证据要求。
- 已有代码入口和文件提示，而非完整仓库内容。
- 所需能力状态、环境变量名称及使用方式。
- 信息请求和门禁状态。
- 上下文预算和省略内容清单。

默认上下文目标为约 12,000 tokens，可按任务配置。引用使用稳定 ID、版本和哈希；Agent 可通过受控工具读取额外引用，但不能浏览整个项目知识库。

上下文检索以结构化依赖和文件映射为主，MVP 不引入向量数据库。

## 14. MCP 协议

MCP 只暴露工作协议，不暴露数据库 CRUD、完整计划或密钥。

### 14.1 工具

- `get_project_brief()`：返回当前蓝图、计划状态、当前工作、最近完成、阻塞、未决信息、安全项目事实和最近项目记忆；不返回本地路径、远程 URL、凭据引用或租约。
- `get_project_memory(before_cursor, limit, include_heartbeats)`：返回游标分页的项目记忆安全投影，默认隐藏心跳。
- `claim_next_work(agent_profile, repository, request_id)`：原子领取一个符合条件的工作项。
- `get_work_context(work_id, lease_token)`：返回任务上下文包。
- `get_work_handoff(work_id, lease_token)`：在有效租约下返回相关前序工作、报告、已知问题、后续事项和阻塞。
- `read_task_reference(work_id, lease_token, reference_id)`：读取授权范围内的额外引用。
- `heartbeat_work(work_id, lease_token)`：续租并记录活动。
- `report_work_blocker(work_id, lease_token, reason, needed_input, proposal)`：报告阻塞并生成信息、决策或变更请求。
- `submit_work_report(work_id, lease_token, report, idempotency_key)`：提交完成报告。
- `release_work(work_id, lease_token, reason)`：释放无法继续的任务。
- `get_capability_status(capability_id, environment)`：查询能力可用状态，不返回凭据。

工具调用必须校验项目、工作项、租约和幂等键。同一任务任意时刻只能有一个有效租约。项目简报和项目记忆只读；任务接力必须先通过租约授权；三者都不得返回租约令牌、Secret、凭据引用、远程 URL 或原始事件 payload。

### 14.2 领取规则

领取过程在一个事务内完成：

1. 按仓库、Agent 能力和任务优先级筛选可执行项。
2. 校验依赖、信息、能力、门禁和路径锁。
3. 创建租约并将任务置为 `claimed`。
4. 写入事件并返回任务契约摘要。

没有可执行任务时返回结构化原因：全部完成、等待人工、等待依赖、能力未就绪或计划为空。

## 15. 完成报告与验收

默认报告结构：

```text
status
summary
branch
commit_sha
changed_files[]
acceptance_results[]
commands_run[]
evidence_refs[]
known_issues[]
follow_up_items[]
contract_hash
idempotency_key
```

阶段 4-6 默认按 `agent_report` 验收，不重新执行测试。阶段 7 在不改变 `AcceptancePolicy` 枚举的前提下，把完成门禁升级为“结构化报告 + 仓库级本地命令验证”。ColdStart 始终执行以下校验：

- 租约、任务和 `contract_hash` 有效。
- 分支符合任务契约，Commit 和文件真实存在。
- 修改路径没有越过允许范围。
- 每条验收标准都有结果说明和所需证据。
- 没有未满足的强制门禁或未处理的硬阻塞。

通过后任务进入 `done`，记录 `completion_source=agent_report`、报告哈希和提交时间。校验失败时任务回到 `in_progress` 或 `blocked`，并返回缺少项；不能直接丢弃 Agent 的有效工作。

Agent 编码任务提交报告后，ColdStart 必须在任务分支上执行领取时固化的仓库验证命令快照。任一必需命令失败、超时或破坏 Git 分支不变量时，任务保持 `in_progress`，报告与脱敏输出保留为一次失败证据；全部命令通过后任务才能进入 `done`。

`human_acceptance` 任务在报告通过结构校验后进入 Inbox。`command_verification` 从阶段 7 起作为 Agent 编码任务的默认完成门禁实现，不再只是预留接口。

## 16. 凭据与第三方能力

- Secret 只存入 Windows Credential Manager 等系统凭据库。
- SQLite 保存 `secretRef`、用途、环境、能力和状态，不保存明文。
- MCP 返回能力状态、接口、环境变量名和使用约束，不返回 Secret 值。
- 任务只能使用其声明的能力；能力授权按任务、环境和范围限定。
- 发布、生产环境和签名证书属于高敏感能力，必须有额外审批策略。
- 日志、事件、错误信息、上下文包和完成报告统一执行敏感值脱敏。
- 开发/测试环境优先使用短期、最小权限凭据；生产 Secret 不提供给 Agent。

威胁模型假设用户信任本地 Agent。ColdStart 防止无意的上下文泄漏和越权计划操作，但不把具有同一 OS 用户 Shell 权限的恶意进程视为可被完全隔离。

## 17. Git 与远程仓库

每个仓库支持多个远程和任意标准 Git 服务。远程配置包括 URL、默认分支、保护分支、认证模式、凭据引用和同步策略。

- GitHub 使用 OAuth Device Flow 获取授权，Token 存入系统凭据库。
- 通用远程支持 HTTPS Credential Helper 和 SSH Agent。
- 产品不依赖 GitHub 网页 DOM。
- 领取任务前检查仓库状态、当前分支和远程最新状态；工作区不干净或分支冲突时不允许领取需要写入的任务。
- 任务工作分支格式为 `codex/<task-key>-<slug>`。
- 报告通过结构校验后，由 ColdStart 自动推送任务分支，不由 Agent 读取远程 Token。
- 推送使用普通推送；冲突时保留本地提交，标记 `sync_failed` 并进入风险提示，不覆盖远程。
- 禁止强制推送、删除远程分支和自动写入保护分支。
- 合并默认分支、创建发布 Tag 和生产部署必须人工审批。

远程推送失败不改变任务完成状态，但会生成同步风险和一条待处理记录。

GitHub 私有仓库创建只允许由桌面 UI 中的明确用户操作发起。用户选择所有者、仓库名和可见性后，系统通过官方 API 创建空仓库，再初始化本地仓库、配置 `origin` 并完成首次推送。MCP 不提供创建、删除或转移仓库的工具；Agent 只能提交建议，实际创建必须由用户确认。

## 18. 需求导入与模型适配

- 支持 Markdown、TXT、DOCX 和 PDF。扫描版 PDF 的 OCR 不在 MVP 范围。
- 导入时保存原文件、文本提取结果、章节/页码锚点和内容哈希。
- 模型输出必须符合 JSON Schema，并保留来源引用、置信度和未决问题。
- 模型只负责提取、归纳、建议和生成说明，不直接修改任务状态或批准门禁。
- 使用 OpenAI 兼容接口，由用户配置模型与 API Key；可指向本地兼容服务。
- 调用外部模型前明确告知项目内容将发送到该服务。
- Prompt 模板随应用版本化，禁止由 Agent 动态修改系统级 Prompt。
- 桌面端可从已映射的 GitHub.com 仓库只读读取开放 Issue，并人工选择单条导入为 Markdown 需求来源；列表最多 50 条，正文最多 30,000 字符，标签、链接和时间均有边界校验。
- Issue 导入复用现有 artifact、来源哈希和锚点体系，固定 `github://owner/repository/issues/number` 来源标识；评论、附件、Projects 和 Milestones 不在导入范围。
- GitHub Token 只进入 Rust 请求头，不进入前端、SQLite、事件、日志或项目文件；Issue 正文只作为不受信任的需求资料，不能触发命令或自动操作。
- 桌面端可按开放、已关闭或全部状态读取 Issue，并在当前最多 50 条快照内按编号、标题、标签、正文预览和导入状态筛选；筛选不触发额外网络请求。

## 19. 桌面 UI

桌面端由以下工作区组成：

- **项目首页**：当前里程碑、可执行任务、阻塞项、人工待办、仓库同步和最近 Agent 运行。
- **人工 Inbox**：按信息、决策、授权、审批和外部操作分类；支持批量处理及长周期预警。
- **需求与蓝图**：文档导入、来源追踪、结构化编辑、蓝图差异、假设与风险。
- **计划看板**：任务列表、依赖视图、关键路径、任务契约、验收策略和计划版本差异。
- **Agent 运行**：活动租约、运行历史、完成报告、证据和异常记录。
- **集成与凭据**：GitHub、OSS、短信、支付等能力状态；只显示凭据引用和授权范围。
- **发布中心**：各平台打包、签名、商店材料、提审任务和人工门禁。
- **设置**：模型提供商、远程仓库、保护分支、审批策略和默认验收策略。

UI 不提供绕过 MCP 或状态机直接修改任务状态的入口。所有调整都通过计划修订、审批或 Inbox 完成。

## 20. 项目变更

需求或架构变化产生新的 `BlueprintRevision`，并执行影响分析：

1. 标记受影响需求、模块、接口、能力和任务。
2. 比较新旧计划，生成计划差异。
3. 保留已完成且仍有效的任务。
4. 对实质变化的执行中任务标记 `stale`，不静默改写契约。
5. 创建必要的迁移、回归和人工决策工作项。

计划修订必须通过 DAG 校验后才能激活。旧版本永久保留，用于审计和回滚。

## 21. 异常与恢复

- **租约超时**：任务回到 `ready`，保留失败运行记录。
- **提交无效**：返回具体缺失项，保留任务和已有证据。
- **上下文过期**：通过 `contract_hash` 检测，拒绝直接完成并标记协调需求。
- **远程冲突**：保留本地提交，任务完成，推送状态单独标记失败。
- **GitHub 授权过期**：能力状态转为 `auth_required`，只阻塞依赖该能力的任务。
- **信息缺失**：仅阻塞声明范围，其他任务继续。
- **模型输出无效**：蓝图不能发布，允许人工修改或重新生成。
- **应用崩溃**：SQLite 事务回滚；事件日志和租约时间戳用于恢复。

## 22. 安全与隐私

- 所有 MCP 调用限定到单一项目和授权工作项。
- Tauri 只暴露显式注册的命令；前端不能任意执行 Shell、读取项目数据库或获取 Secret。
- 路径校验防止上下文和证据读取越界。
- 外部文档和代码内容始终视为不可信数据，不当作系统指令。
- 生成的 `AGENTS.md` 明确要求通过 MCP 领取任务、一次执行一个任务、不得读取密钥、不得绕过门禁。
- 远程推送由 ColdStart 执行，Agent 不接收 Token。
- 高危动作分为生产部署、发布、审批、破坏性操作和费用授权，必须经过策略引擎。
- 单机项目数据默认不上传；用户启用外部模型时，仅发送当前操作所需内容。

## 23. 测试策略

- **Rust 单元测试**：状态机、DAG 校验、信息阻塞范围、策略引擎、上下文预算和脱敏。
- **Rust 集成测试**：SQLite 事务与并发领取、租约超时、事件投影、文件快照和 Git 同步。
- **MCP 契约测试**：工具 schema、幂等、错误码、权限边界和无 Secret 响应。
- **前端测试**：组件和关键交互流程；端到端测试覆盖创建项目、导入需求、生成蓝图、生成计划和模拟 Agent 领取与提交。
- **Git 测试**：使用本地裸仓库验证克隆、拉取、任务分支推送、保护和冲突处理。
- **安全测试**：路径越界、日志脱敏、Prompt 注入、过期租约和越权能力访问。

## 24. MVP 范围与验收

MVP 交付桌面客户端和完整控制闭环，但不交付发布自动化。

必须实现：

- 项目、多个仓库和平台目标配置。
- 需求导入与结构化蓝图。
- 信息请求、人工 Inbox 和审批门禁。
- 计划生成、编辑、依赖和验收策略。
- 本地凭据引用和三方能力状态。
- GitHub 私有仓库创建、远程配置和任务分支自动推送。
- 仓库级本地验证命令配置与完成门禁：Agent 报告后由 ColdStart 在任务分支真实执行构建/测试，通过后才完成任务。
- MCP 任务领取、上下文、心跳、阻塞和完成报告。
- 证据、事件、运行记录和计划看板。

MVP 验收场景：

1. 新建一个包含服务端、管理后台和小程序的项目。
2. 导入需求并生成蓝图，系统只请求缺失且阻塞的信息。
3. 生成任务 DAG，其中包含编码、外部账号和发布门禁任务。
4. Codex 通过 MCP 依次领取两个仓库中的任务并提交结构化报告。
5. 报告通过后计划自动推进，任务分支自动推送到远程。
6. 缺失信息和发布审批在 Inbox 中处理，不阻塞无关任务。
7. 所有 MCP 响应、日志和 Git 仓库中都不存在明文密钥。
8. Agent 编码仓库未配置验证命令、命令失败或命令超时时，任务不能进入 `done`；修复后可通过新的报告尝试完成。

## 25. 实施顺序

1. **基础设施**：Rust workspace、Tauri 壳、SQLite、迁移、事件日志、凭据引用和模板加载。
2. **蓝图能力**：文档导入、模型适配、结构化需求、蓝图层、来源追踪和信息请求。
3. **计划与 MCP**：计划编译、DAG、状态机、租约、上下文编译和完成报告。
4. **仓库与能力**：Git 状态、GitHub OAuth、远程推送、三方能力状态和审批策略。
5. **闭环与加固**：React 桌面 UI 完整流程、变更重规划、Rust 与前端测试、安全校验和 Tauri 打包。

## 27. 阶段 4 详细边界（已确认）

阶段 4 交付计划引擎、任务执行状态机与 MCP stdio 工作协议，不提前伪造后续阶段的 Git、凭据和发布能力。

### 27.1 计划编译

- 计划由确定性模板从最新已发布蓝图生成，不再次调用模型；模板版本固定为 `plan-v1`。
- `PlanRevision` 不可变，发布前校验任务键、依赖引用、阻塞依赖环、验收项和路径范围。
- `taskKey` 从蓝图实体 ID 和任务类别稳定推导，不使用随机 UUID。
- 任务顺序为：平台工程基础、服务端契约、模块与平台纵向切片、三方能力准备与接入、发布前置事项、平台发布里程碑。
- 每个编码任务只覆盖一个模块和一个平台。逻辑仓库键为 `server`、`admin`、`web`、`app`、`mini_program`，真实仓库映射由阶段 5 绑定。
- 阶段 4 只激活首个已发布计划；新计划修订后的状态继承、契约 `stale` 和变更影响分析属于阶段 6。

### 27.2 人工任务

- 平台账号、资质、能力准备和发布条件生成 `human_external` 或 `approval_gate` 任务。
- 人工任务进入统一 Inbox，可凭说明与可选证据被人工接受或拒绝。
- 编码任务不能由桌面 UI 直接标记完成，只接受带有效租约的 MCP 结构化报告。

### 27.3 状态、租约与报告

- `blocks` 依赖决定领取资格，`informs` 只参与上下文，`conflicts_with` 进入任务上下文和资源锁提示。
- SQLite 使用 `BEGIN IMMEDIATE` 原子领取；同一任务至多一个有效租约，同一逻辑仓库默认一个活动资源锁。
- 默认租约 30 分钟，心跳间隔建议 5 分钟；过期租约在后续操作时惰性回收，不依赖常驻进程。
- 租约令牌为随机 256 位值，SQLite 只保存 SHA-256 哈希；令牌不得进入事件、日志、UI 或报告回放。
- 默认上下文预算为约 12,000 tokens，使用确定性估算与结构化引用，不引入向量检索。
- 授权类项目事实在 Agent 上下文中只显示为“已登记”，具体值不展开。
- 阶段 4 报告校验租约、契约哈希、验收项覆盖、修改路径、证据引用和幂等键；不重跑测试，不校验 Git 中 Commit 是否真实存在。

### 27.4 MCP 与桌面观察

- 新增独立二进制 `coldstart-mcp --project-home <path>`，使用官方 `rmcp` Rust SDK 和 stdio 传输。
- MCP 只提供 `claim_next_work`、`get_work_context`、`read_task_reference`、`heartbeat_work`、`report_work_blocker`、`submit_work_report`、`release_work`。
- Codex 主动领取任务，ColdStart 不启动 Codex。桌面 UI 通过刷新、焦点事件和短轮询观察 MCP 写入的状态。
- 计划看板提供计划生成、编辑、发布、任务与依赖查看、租约与报告查看、人工任务处理和 MCP 启动配置复制。

### 27.5 阶段 4 明确不做

- Git 仓库映射、真实 Commit 校验、任务分支推送和 GitHub 操作。
- 系统凭据库、真实 OSS/短信/支付连接和 Secret 注入。
- 自动部署、App 打包、商店提审、小程序发布和命令自动验证。
- 已激活计划的重规划与任务状态继承。

## 28. 阶段 5 详细边界（已确认）

阶段 5 交付代码仓库映射、Git 同步、系统凭据引用、三方能力状态、GitHub 私有仓库创建和只读发布中心。外部部署、App 打包与商店提审仍不自动执行。

### 28.1 仓库与 Git

- 每个项目可按逻辑键配置多个已有 Git 仓库，逻辑键固定为 `server`、`admin`、`web`、`app`、`mini_program`。
- 仓库配置包含绝对本地路径、远程 URL、默认分支、保护分支、认证模式、可选凭据引用和同步策略。
- 保存前验证路径是 Git 工作树；远程 URL 不允许包含内嵌用户名或密码。
- 领取编码任务时，如果该逻辑键已配置仓库，ColdStart 先检查工作区干净、获取远程、验证基准分支并按任务契约创建 `codex/*` 工作分支。
- 工作区不干净、分支已存在、远程不可用或认证失败时，释放刚创建的租约并返回稳定错误，不覆盖本地或远程历史。
- Agent 报告完成后，ColdStart 验证 Commit、任务分支和实际变更文件；验证通过后才接受报告。
- 接受报告后自动执行普通推送；推送失败不改变任务完成状态，但记录 `git_syncs` 风险和错误摘要。禁止强推、删除远程分支和写入保护分支。

### 28.2 凭据与能力

- 明文 Secret 只写入 Windows Credential Manager；SQLite 只保存 `secretRef`、名称、提供方、类型、环境和状态。
- 桌面端写凭据后不提供回读接口；删除元数据时同步删除系统凭据条目。
- 三方能力从最新已发布蓝图中同步为项目级能力视图，环境固定为 `development`、`staging`、`production`。
- 能力状态为 `missing`、`configured`、`verified`、`auth_required`、`disabled`，可关联一个凭据引用。
- MCP 增加 `get_capability_status`，只返回能力状态、提供方、环境和凭据引用标识，不返回值。

### 28.3 GitHub

- 支持导入本机 GitHub CLI 已有登录 Token，导入后 Token 立即写入系统凭据库，界面只显示账号和授权范围。
- 支持用户提供 GitHub OAuth App Client ID 后启动 Device Flow；应用不内置伪造的 Client ID 或客户端 Secret。
- 创建私有仓库必须由桌面 UI 中的明确用户操作发起。输入仓库名、描述和目标本地仓库后，通过官方 REST API 创建，再配置 `origin`。
- MCP 不提供创建、删除或转移仓库的能力，Agent 只能建议。
- 认证 Token 不进入 Tauri 响应、SQLite、事件、日志、错误、任务上下文或 MCP。推送 GitHub 时仅在 Rust 子进程环境中短暂注入认证头。

### 28.4 发布中心

- 发布中心汇总最新已发布计划中的 `release-prereq:*`、`release:*`、`approval_gate` 和人工外部任务。
- 发布中心显示每个平台里程碑、前置条件、阻塞状态、完成说明和最近人工操作，不执行部署、打包或提审。
- 高风险任务继续通过统一 Inbox 完成；MCP 和 Agent 不能批准 `approval_gate`。

### 28.5 阶段 5 明确不做

- 自动合并受保护分支、创建 Release Tag、部署生产或自动提交应用商店/小程序审核。
- 从空目录自动生成业务代码或伪造初始 Commit。
- 通用 OAuth 提供商、令牌刷新、组织级 GitHub App 安装和多用户授权。
- 将 Secret 注入 Agent 上下文；任务只获得环境变量名称和能力状态。

## 29. 阶段 6 详细边界（已确认）

阶段 6 完成 MVP 的集成与加固，重点交付安全变更重规划、跨子系统验收、可安装的 Windows 桌面包和最终安全门禁。阶段 6 不扩大目标平台，不增加发布自动化。

### 29.1 安全变更重规划

- 已激活计划只有在项目没有活动租约时才能被新计划替换。存在活动租约时，预览显示阻塞原因，发布事务再次校验并拒绝；Agent 必须完成、释放租约或等待租约过期。
- 发布前必须生成只读计划差异预览。预览包含新增、契约变化、未变化和已删除任务，以及继承完成、重新打开和取消数量。
- 桌面 UI 必须展示预览，并由用户再次确认后才允许替换当前已发布计划。MCP 不提供计划发布、确认或回滚工具。
- 发布新计划时，旧计划状态改为 `superseded`，历史计划、任务契约、报告和事件永久保留。
- 任务身份以稳定 `task_key` 表达，契约以规范化任务 JSON 的 SHA-256 表达。新旧计划按 `task_key` 对齐，不按数据库行 ID 对齐。
- 未变化且已完成的 Agent、人工或审批任务保持 `done` 并保留完成时间；未变化且未完成的任务保留原状态，再由依赖刷新决定可领取状态。
- 契约发生变化的任务在新计划中重新打开，不静默沿用旧完成结果；旧计划中对应工作项标记 `contract_state = stale`。
- 新计划中不存在的旧任务不再出现在活动计划；旧计划中未完成项标记取消，旧契约标记 `stale`。已完成的历史项保留完成状态，不重写完成事实。
- 新任务初始为草稿并按依赖刷新。取消状态不自动解锁依赖它的新任务，预览和计划警告必须让用户可发现此类阻塞。
- 旧计划的工作项、租约和报告不能推进新计划。任何心跳、报告、阻塞或人工完成操作都必须验证工作项属于当前活动计划且契约不是 `stale`。
- 计划发布、旧计划替换、状态继承和任务取消在同一 SQLite 事务中完成；任一校验失败时全部回滚。

### 29.2 跨子系统验收

- MVP 验收覆盖“创建项目 -> 导入需求 -> 发布蓝图 -> 编译并发布计划 -> Codex/MCP 领取 -> 真实 Git 分支与 Commit -> 报告验收 -> 推送 -> 发布中心 -> 重启恢复”的完整闭环。
- 变更重规划验收覆盖同契约完成任务继承、变化契约重新打开、新增任务解锁、删除任务取消、活动租约拒绝和旧工作项越权拒绝。
- 自动化测试使用本地裸 Git 远程，不依赖真实 GitHub 账号；真实私有仓库创建仍必须由用户在桌面 UI 现场确认。
- MCP 契约测试必须验证响应、错误和 stderr 不包含 Secret、租约令牌或数据库内部路径。
- 重启验收必须证明计划版本、任务状态、报告、Git 同步、仓库映射、凭据元数据和能力状态保持可用。

### 29.3 安装与分发

- Windows 安装包使用 Tauri NSIS，面向当前用户安装，不要求管理员权限，不加入自动更新。
- 安装器允许用户选择安装目录，并验证可以安装到 D 盘；卸载必须移除程序文件和开始菜单入口，不删除用户项目数据。
- 桌面二进制、MCP 二进制、Web 资源和应用图标包含在安装包中；从安装目录启动后仍能定位 MCP 二进制。
- 安装包未做代码签名，交付时明确标注 Windows SmartScreen 可能提示未知发布者，不宣称已签名。
- 构建缓存、依赖和安装包输出继续优先放在 D 盘。

### 29.4 安全加固

- Tauri 只注册显式命令，不启用 Shell、任意文件系统、任意 HTTP 请求或自动更新插件。
- 生产 CSP 只允许应用自身资源与 Tauri IPC；开发 CSP 单独允许本地 Vite 地址，不能把开发服务器来源带入生产包。
- Tauri 响应的错误必须使用稳定错误码和脱敏信息，不回显 Secret、Token、租约令牌或完整数据库行。
- 凭据写入、删除和项目范围校验保持现有语义；SQLite 全文本列、事件、报告、MCP 响应和错误序列化扫描不得出现测试 Secret。
- 上下文与证据路径继续拒绝绝对路径、盘符路径、`..` 和符号链接越界。

### 29.5 阶段 6 明确不做

- 多人协作、云同步、账号体系和远程控制平面。
- 自动合并、Release Tag、生产部署、商店提审或小程序发布。
- 代码签名证书采购、自动更新、崩溃上报服务和安装使用统计。
- 通用平台扩展、插件市场、任意 MCP 写工具或绕过桌面确认的计划发布。

## 30. 阶段 7 详细边界（已确认）

实现状态：已完成（2026-10-31）。仓库验证命令、SQLite v6 快照与状态机、Windows Job Object 执行器、Git 不变量校验、应用层编排、Tauri/React 编辑器、MCP 错误详情、真实 Git + 真实 `.exe` 端到端测试和 NSIS 安装验收均已落地；本阶段没有扩大到云 CI、远程执行器或自动修复。

阶段 7 交付“本地命令验证与完成门禁”。Codex 仍只通过 MCP 主动领取和上报，ColdStart 只认 Codex 的结构化完成报告；但报告本身不再等于完成，ColdStart 必须独立执行仓库配置的构建或测试命令。

### 30.1 严格领取门禁

- 每个 `agent_coding` 任务所属仓库在领取时必须至少有一条验证命令。
- 没有验证命令时，领取事务返回结构化原因 `verification_not_configured`，不创建租约，不改变任务状态。
- 领取流程在同一 SQLite 事务中校验验证配置、创建租约并把配置快照写入 `work_runs`；任一写入失败时整体回滚。
- 验证配置属于仓库，不属于单个任务。第一版不支持任务级命令覆盖或临时跳过。
- 验证配置的修改只影响后续领取；已领取任务始终使用快照，桌面端改配置不能追溯改变当前任务门禁。

### 30.2 验证命令模型

新增仓库级验证命令，桌面端拥有完整读写权限，MCP 只能通过任务上下文读取快照，不能创建、修改、删除或临时替换命令。

每条命令包含：

- `name`：仓库内唯一，1-80 个字符，只用于展示和失败定位。
- `executable`：已解析的绝对 Windows `.exe` 路径；不接受相对路径、`.cmd`、`.bat`、`.ps1` 或目录。
- `args`：字符串数组，每个参数独立保存，不经过 Shell 拼接、变量展开或通配符展开。
- `timeoutSeconds`：10-900 秒。
- `position`：仓库内执行顺序。

约束如下：

- 每个仓库最多 8 条命令，全部为必需命令；总计超时预算不超过 3600 秒。
- 命令名称在同一仓库唯一；参数合计长度上限为 16 KiB，单个参数上限为 2048 个字符。
- 可执行文件在保存时验证存在、是普通文件、扩展名为 `.exe`，并保存规范化后的绝对路径。
- 命令工作目录固定为仓库根目录，不能单独配置；不提供 Shell、环境变量插值、命令串联、重定向或管道语法。
- 命令配置属于普通项目配置，用户不得把 Secret 写入命令或参数；系统不提供从 Credential Manager 读取 Secret 并注入命令的能力。

### 30.3 领取快照与任务上下文

- `work_runs` 增加 `verification_snapshot_json` 和 `verification_snapshot_hash`。快照包含有序命令、名称、绝对可执行路径、参数、超时和总预算。
- 快照哈希使用规范化 JSON 的 SHA-256；报告、验证记录和任务上下文都引用同一哈希。
- `get_work_context` 返回验证快照，让 Codex 在开发阶段提前运行相同检查；ColdStart 在报告阶段仍会独立重跑，不信任 Agent 自报的命令结果。
- 任务上下文中只展示与当前仓库相关的快照，不展示其他仓库、凭据或系统环境变量值。

### 30.4 提交、执行与状态回退

`submit_work_report` 的执行顺序固定为：

1. 校验工作项属于当前活动计划、租约有效、报告状态为 `completed`、契约哈希和验收证据完整。
2. 校验报告分支、Commit、修改文件和允许路径与真实 Git 仓库一致。
3. 读取领取时固化的验证快照；缺失快照时拒绝完成并返回 `verification_not_configured`。
4. 将当前租约延长到“命令总超时预算 + 5 分钟”，把任务置为 `submitted`，创建 `running` 验证记录并提交事务。
5. 在任务分支上按顺序执行命令；执行前后都校验当前分支、`HEAD` 仍等于报告 Commit，且没有已跟踪文件被命令修改。
6. 全部成功时在事务中写入 `passed`，报告标记接受，租约消费，运行完成，任务进入 `done` 并刷新依赖。
7. 任一失败、超时、启动失败或 Git 不变量被破坏时写入 `failed`，报告标记拒绝并保存脱敏输出，任务回到 `in_progress`，租约保持有效，允许同一 Agent 修复后重新报告。
8. 只有任务成功进入 `done` 后才执行现有远程推送；推送失败仍只记录 Git 同步失败，不回写任务状态。

失败语义：

- 非零退出码、无法启动、超时、命令修改已跟踪文件、切换分支或改写 `HEAD` 都视为验证失败。
- 失败返回具体命令名称、失败类型、退出码、耗时和有限输出摘要；不返回租约令牌、Secret 或完整环境。
- 同一报告幂等键在 `running` 时返回 `verification_in_progress`；已完成时返回原报告记录。失败后重试必须使用新的幂等键。
- 同一工作项最多存在一条 `running` 验证记录，由部分唯一索引保证。
- 租约在命令执行期间过期、桌面进程崩溃或验证记录长期停留在 `running` 时，租约过期处理必须把运行标为 `expired`、报告标为 `interrupted`、任务回到 `ready`，旧报告不能推进完成。

### 30.5 进程执行、超时与环境边界

- 使用 `std::process::Command` 直接执行绝对 `.exe` 路径和参数数组，不经过 PowerShell、`cmd.exe` 或其他 Shell。
- 标准输入设为空；标准输出和标准错误并发读取，避免子进程因管道写满而死锁。
- 每个命令创建 Windows Job Object，并启用关闭即终止；超时时终止整个 Job，确保子进程树被清理。Job 创建或分配失败时不执行命令并记录基础设施失败。
- 进程环境先清空，再只注入必要白名单：`SystemRoot`、`WINDIR`、`PATH`、`PATHEXT`、`TEMP`、`TMP`、`USERPROFILE`、`LOCALAPPDATA`、`APPDATA`、`ProgramFiles`、`ProgramFiles(x86)`、`CommonProgramFiles`、`ComSpec`、`HOME`、`USERNAME`，以及显式配置的 `CARGO_HOME`、`RUSTUP_HOME`、`PNPM_HOME`、`NODE_HOME`、`JAVA_HOME`、`ANDROID_HOME`、`ANDROID_SDK_ROOT`、`GRADLE_USER_HOME`。
- 不继承 `NODE_OPTIONS`、`GITHUB_TOKEN`、`GH_TOKEN`、`*_SECRET`、`*_PASSWORD`、`*_API_KEY` 或 Credential Manager 中的任何值。
- 命令仍以当前 Windows 用户权限运行，不是文件系统或网络沙箱；安全边界是“MCP 不能注入命令或 Secret”，不宣称恶意构建脚本无法访问用户文件。
- 每个输出流最多保留 32 KiB，合并后最多保留 64 KiB 尾部；截断时写入明确标记。输出去除 ANSI、控制字符，并对常见 Bearer、Token、Password、Secret 和 API Key 形式做尽力脱敏。
- 原始输出不得写入日志、事件、SQLite、MCP 响应或错误；只持久化脱敏后的有限文本。

### 30.6 持久化、事件与桌面展示

- SQLite 架构版本升级到 6，新增 `repository_verification_commands`，并给 `work_runs` 与 `work_reports` 增加验证快照、状态、结果和时间字段。
- 验证状态固定为 `not_required`、`running`、`passed`、`failed`、`interrupted`；`accepted` 只在验证通过后变为真。
- `verification_json` 保存快照哈希、每个命令的名称、退出码、耗时、输出摘要、截断标记、失败类型和整体时间，不保存原始输出。
- 新增验证开始、通过、失败和中断事件；现有报告提交与任务完成事件继续按最终结果写入。
- 集成与凭据页的每个仓库提供验证命令列表，支持新增、编辑、删除和排序；使用文件选择器选择 `.exe`，参数按“每行一个”编辑并映射为字符串数组。
- 仓库没有任何验证命令时，界面必须显示不可领取警告；任务看板显示最近一次验证状态、失败命令和脱敏输出摘要。
- Tauri 只新增明确的验证命令读写命令；前端不能传入任意工作目录、环境变量或 Shell 命令。

### 30.7 MCP 与错误码

- 不增加 MCP 命令配置工具；`submit_work_report` 的职责扩展为触发并等待本地验证。
- `get_work_context` 返回 `verification` 快照；`submit_work_report` 返回包含验证结果的报告记录。
- 新增稳定错误码：`verification_not_configured`、`verification_in_progress`、`verification_failed`、`verification_timeout`、`verification_interrupted`、`verification_command_invalid`。
- MCP 错误和工具结果不得包含原始输出、租约令牌、Secret、完整环境变量或数据库内部路径。

### 30.8 测试与阶段验收

- 领域测试覆盖命令名称、路径、参数、超时、总量和快照哈希校验。

- 前端测试覆盖验证命令新增/编辑/删除/排序、不可领取警告、任务验证状态和失败输出摘要。

### 30.9 阶段 7 明确不做

- 云 CI、远程执行器、容器沙箱、Windows 用户隔离或命令权限沙箱。

## 31. 阶段 12：GitHub 草稿 PR 交付

实现状态：已完成（2026-11-13）。详细设计见 `docs/superpowers/specs/2026-11-13-coldstart-draft-pull-request-design.md`。

阶段 12 在现有“验证、Review、推送任务分支”闭环之后，增加人工触发的 GitHub 草稿 PR 出口。它不改变 MCP 主动领取协议，也不把 Agent 报告当作可合并证据。

### 31.1 创建条件

- 编码任务为 `done`，报告已接受且结果为 `completed`。
- Review 状态为 `not_required`、`passed` 或 `waived`。
- 报告分支与 Commit 存在匹配的成功推送记录。
- 仓库远程为 GitHub.com 的 HTTPS 或 SSH 地址。
- 仓库使用 GitHub OAuth Token 或 Personal Access Token 凭据。

### 31.2 数据与事件

- SQLite 架构升级到 8，新增 `pull_requests`；同一报告只允许一个 PR，同一仓库内编号唯一。
- 保存编号、HTTPS 链接、标题、分支、状态、草稿标记和更新时间。
- 记录 PR 打开和状态变更事件；状态只在状态或草稿标记变化时写事件。
- 项目记忆只投影编号、状态和稳定引用，不返回 Token、请求正文或本地路径。

### 31.3 人工与安全边界

- 创建与刷新只由桌面端人工触发，MCP 工具总数仍为 11，不增加 PR 写工具。
- 请求固定 `draft: true`；不合并、不关闭、不转正式 PR、不写评论、不读取 Checks、不创建 Tag。
- PR 正文由服务端从任务和报告生成，限制数量与长度，复用验证输出脱敏器。
- Token 只进入 Rust HTTP Authorization 头，不进入 SQLite、事件、Tauri 响应、前端状态、日志或错误。
- 重复创建返回本地已有记录，不重复调用 GitHub。

### 31.4 验收与限制

- 适配器、存储、应用、前端和真实本地 Git 推送闭环均有自动化测试。
- 支持 GitHub.com，不支持 Enterprise Server、PR Checks、Review 评论、冲突检测或自动合并。
- 如果 GitHub 创建成功但本地保存失败，重试可能产生重复远程 PR；当前以本地幂等为主。
- 阶段 13 在保留上述阶段 12 边界的前提下，另行增加了 Checks、Review 与行内评论的桌面端只读同步。

## 32. 阶段 13：GitHub PR 验收信息只读同步

实现状态：已完成（2026-11-13）。详细设计见 `docs/superpowers/specs/2026-11-13-coldstart-pr-insights-design.md`。

阶段 13 为已存在的草稿 PR 增加人工触发的验收信息同步，使最终合并前可以在 ColdStart 内同时核对平台检查结果与历史 AI Review。它不把 GitHub 状态变成自动决策依据，也不改变任务状态机或 MCP 协议。

### 32.1 同步范围

- 使用四个只读 `GET`：PR 详情、当前 head 提交的 Checks、Review 列表和行内评论列表。
- 只有桌面端人工点击“刷新状态”才访问 GitHub；MCP 工具总数仍为 11。
- Checks 汇总分为 `none`、`pending`、`success` 和 `failure`；失败、超时、取消、启动失败与需要操作都归入 `failure`。
- Review 与 Checks 的未知平台状态映射为 `unknown`，不推断为通过。
- 每次最多读取 100 个 Checks、100 条 Review 和 100 条行内评论，只读取第一页，不自动翻页。

### 32.2 持久化与界面

- SQLite 架构升级到 9，新增 `pull_request_insights`；每个 PR 最多一份快照，删除 PR 或项目时级联删除。
- 快照包含 Checks、Review、行内评论、内容哈希和同步时间；正文、作者、路径与链接先脱敏、限长和校验。
- 内容变化时写入 `PullRequestInsightsSynced` 项目事件；重复刷新相同内容只更新时间，不制造重复事件。
- “AI 评审”历史展示 Checks 汇总、Review 结论与正文、行内评论的文件路径和行号、同步时间及未同步提示。
- 外部正文只按纯文本渲染，链接必须为 HTTPS，并使用安全的新窗口属性。

### 32.3 安全边界

- 不回复、解决或删除评论。
- 不重跑 Checks，不创建 Check Run，不写 Commit Status。
- 不合并、关闭、转正式 PR、更新分支或创建 Tag。
- Token 只进入 Rust HTTP Authorization 头，不进入 SQLite、事件、Tauri 响应、前端状态、日志或错误。

### 32.4 验收与限制

- 领域、适配器、存储、应用和前端测试覆盖四接口读取、状态汇总、上限、脱敏、失败不落半套数据与幂等事件。
- 现有项目数据库从架构 8 自动升级到 9，项目、工作项与既有 PR 数据保留。
- 阶段 13 当时仅支持 GitHub.com；不读取冲突状态、部署状态、Issue 或 Projects。后续阶段 14-16 已增加合并状态、冲突定位与头提交部署状态，阶段 17-19 已增加 Issue 人工导入与 Projects 只读概览。
- 失败的 Checks 和 Review 只用于人工判断，不触发自动修复、自动重跑或自动合并。
- 阶段 14 增加了 PR 详情中的合并状态展示，但仍不提供自动合并。

## 33. 阶段 14：GitHub PR 合并就绪只读展示

实现状态：已完成（2026-11-13）。详细设计见 `docs/superpowers/specs/2026-11-13-coldstart-pr-merge-readiness-design.md`。

阶段 14 在阶段 13 的 PR 验收快照上增加合并就绪信息，帮助人工在最终合并前识别已知阻塞项。它不增加 GitHub 请求，不改变 SQLite 架构，也不授予任何合并能力。

### 33.1 数据映射

- 复用 PR 详情响应中的 `mergeable` 与 `mergeable_state`。
- 稳定映射为 `mergeable`、`conflicted`、`blocked`、`behind`、`unstable`、`draft`、`checking` 和 `unknown`。
- 无法识别的状态或缺失字段默认为 `unknown`，不推断为可合并。
- `mergeable_state` 只保留稳定枚举，原始文本限长后丢弃，不进入事件、日志或错误。

### 33.2 快照兼容与界面

- 合并状态写入既有 `pull_request_insights` JSON，不升级 SQLite 架构。
- 旧快照缺少该字段时默认为 `unknown`，刷新后才会得到新状态。
- 开放 PR 展示合并状态徽标与“合并前检查”，列出冲突、阻塞、落后、草稿、状态未知、Checks 失败/未完成和 Review 要求修改。
- 已合并或已关闭 PR 展示终态，不再展示合并前检查。
- 没有已知阻塞项时明确说明这只是当前快照，不构成自动合并许可。

### 33.3 安全边界

- 不增加 GitHub 端点；仍只有阶段 13 的四个只读 GET。
- 不调用合并、关闭、更新分支、重跑 Checks、创建 Check Run 或回复评论接口。
- 阶段 14 当时不展示具体冲突文件、不读取部署状态；阶段 15-16 已增加这两项。阶段 17-18 增加 Issue 人工导入，阶段 19 增加 Projects 只读概览；Project 条目仍不会导入需求或计划。
- 不增加 MCP 工具，MCP 总数仍为 11。

### 33.4 验收

- 领域测试覆盖全部状态映射、缺失信号和旧快照默认值。
- 适配器测试覆盖合并状态字段和非法状态长度。
- 应用测试覆盖刷新后快照持久化合并状态。
- 前端测试覆盖合并冲突、合并前阻塞项、已合并终态和只读说明。
- 全量门禁、安装包和 D 盘覆盖安装通过。

## 34. 阶段 15：GitHub PR 冲突文件本地定位

实现状态：已完成（2026-11-13）。详细设计见 `docs/superpowers/specs/2026-11-13-coldstart-pr-conflict-locator-design.md`。

阶段 15 在 GitHub 已标记合并冲突时，用本地 Git 对象定位冲突路径。它补充阶段 14 的合并前检查，不改变 GitHub 的冲突判断，也不提供冲突解决或分支更新能力。

### 34.1 数据模型

- `PullRequestInsights` 增加带默认值的 `conflictDetails`，写入既有 JSON 快照，不升级 SQLite 架构。
- 状态为 `not_checked`、`not_applicable`、`detected`、`not_reproduced`、`unavailable`。
- `detected` 最多保存 100 条仓库相对路径，每条最多 1,024 字符；不保存补丁、blob 内容或 Git 原始输出。
- 旧快照缺少该字段时默认为 `not_checked`，刷新后才执行诊断。

### 34.2 诊断边界

- 只有开放且 `mergeability=conflicted` 的 PR 才使用 GitHub 返回的 base/head SHA 执行本地诊断。
- `git merge-tree --write-tree --name-only --no-messages` 退出码 0 表示本地未复现，1 表示检测到冲突，其他退出码或缺失对象表示不可用。
- 诊断不 fetch、不切换分支、不修改工作区/索引/远程；Git 可能在 `.git` 中写入临时树对象。
- 禁用系统/全局 Git 配置，覆盖仓库本地全部 `merge.*.driver`，强制 `merge.default=text`，防止只读刷新执行仓库自定义 merge driver。
- 本地诊断失败不阻断 GitHub 状态、Checks、Review 和评论快照落库。

### 34.3 界面与安全

- 开放冲突 PR 显示“本地冲突定位”，区分已定位、未复现、不可用和旧快照未检查。
- 本地未复现不表示冲突已解决，GitHub 状态仍是最终依据。
- 不新增 GitHub 端点，不增加 MCP 工具，不自动解决冲突、更新目标分支或合并。

### 34.4 验收

- 领域测试覆盖默认值、状态一致性、路径上限和控制字符。
- Git 适配器测试覆盖冲突路径、干净合并、缺失提交和自定义 merge driver 不执行。
- 应用测试覆盖真实冲突路径持久化，以及本地诊断失败不阻断 GitHub 快照。
- 前端测试覆盖四种冲突诊断状态和只读说明。
- 全量门禁、安装包、D 盘覆盖安装与 11 个 MCP 工具验收通过。

## 35. 阶段 16：GitHub PR 部署状态只读展示

实现状态：已完成（2026-11-13）。详细设计见 `docs/superpowers/specs/2026-11-13-coldstart-pr-deployment-status-design.md`。

阶段 16 在现有 PR 验收快照中增加当前 PR 头提交的 GitHub Deployment 记录与最新 Deployment Status，用于人工判断部署环境是否已针对本次提交运行。它不构成生产发布或合并许可，也不提供任何部署写操作。

### 35.1 数据映射

- 使用 `GET /repos/{owner}/{repository}/deployments?sha={head_sha}&per_page=11` 读取当前 PR 头提交的部署。
- 使用 `GET /repos/{owner}/{repository}/deployments/{deployment_id}/statuses?per_page=1` 读取每个部署的最新状态。
- 请求 11 条用于判断截断，最多保存 10 条部署；环境名最多 200 字符，描述最多 500 字符。
- 不保存 payload、creator、ref、environment URL、日志 URL 或 GitHub 原始响应。

### 35.2 快照与失败降级

- `PullRequestInsights` 增加带默认值的 `deploymentDetails`，写入既有 JSON 快照，不升级 SQLite 架构。
- 旧快照缺少该字段时默认为 `not_checked`，刷新后才读取部署。
- 原有 PR、Checks、Review 和评论四个请求仍保持原子边界；四个请求成功后才会读取部署。
- 部署列表请求失败时保存 `unavailable`，不阻断其他 PR 验收信息落库。
- 单个部署状态请求失败时只将该部署标记为 `unknown`，其他部署继续展示。
- 状态稳定映射为 `success`、`failure`、`error`、`inactive`、`in_progress`、`queued`、`pending` 和 `unknown`。

### 35.3 界面与安全

- PR 验收区增加部署汇总徽标和部署详情，区分成功、失败、进行中、未知、无部署、不可用与旧快照未同步。
- 展示环境名、状态、描述和状态更新时间，并明确数据仅来自当前 PR 头提交的快照。
- 不提供部署、审批、取消、重试、回滚或日志跳转操作。
- 不增加 MCP 工具，MCP 总数仍为 11；Agent 不能主动刷新 PR 或读取部署信息。

### 35.4 验收

- 领域测试覆盖状态映射、默认值、数量上限、状态一致性和文本校验。
- GitHub 适配器测试覆盖精确头提交查询、截断、最新状态解析和非法响应。
- 应用测试覆盖成功落库、列表失败降级、单状态失败降级和旧快照兼容。
- 前端测试覆盖成功、失败、进行中、未知、无部署、不可用和旧快照提示。
- 全量门禁、安装包、D 盘覆盖安装、11 个 MCP 工具和 SQLite 架构 9 数据保留验收通过。

阶段 18 增强 Issue 需求收件箱，使历史项目中已关闭的需求也能被人工检索和导入，并在当前读取快照内提供轻量筛选。它不引入 GitHub Search API、自动翻页、后台轮询或任何 Issue 写入能力。

## 36. 阶段 17：GitHub Issue 需求收集与导入

实现状态：已完成（2026-11-13）。详细设计见 `docs/superpowers/specs/2026-11-13-coldstart-github-issue-intake-design.md`。

阶段 17 为已有项目和迭代需求增加一个受控入口：从已映射的 GitHub.com 仓库读取开放 Issue，由人在桌面端选择并导入为本地需求来源，再沿用现有蓝图、计划和 MCP 领取流程。它不把 GitHub Issue 变成自动任务，也不扩大 Agent 权限。

### 36.1 数据映射

- 开放列表使用 `GET /repos/{owner}/{repository}/issues?state=open&sort=updated&direction=desc&per_page=100`，过滤 GitHub 返回的 Pull Request。
- 列表最多向桌面端返回 50 条并标记截断；标题最多 256 字符，正文最多 30,000 字符，标签最多 20 个且每个最多 50 字符。
- 导入单个 Issue 时重新读取 `GET /repos/{owner}/{repository}/issues/{issue_number}`，不使用可能过期的列表正文。
- 只接受 GitHub.com HTTPS 链接和有效 RFC 3339 时间；拒绝非法状态、控制字符、超长文本、超大响应和 Pull Request 条目。

### 36.2 本地来源与持久化

- Issue 转换为固定格式 Markdown，包含标题、仓库、状态、评论数说明、更新时间、链接、来源标识、标签和正文。
- 文件名固定为 `github-issue-<number>.md`，复用现有 artifact 目录、内容哈希和 Markdown 锚点抽取。
- `importSource` 固定为 `github://owner/repository/issues/number`，用于展示已导入状态和阻止重复导入。
- 重复导入返回稳定错误 `github_issue_already_imported`，不创建重复 artifact；不升级 SQLite 架构。
- 评论不导入。正文只作为外部需求资料，不执行其中链接、命令或代码块。

### 36.3 桌面与安全边界

- 需求导入页增加仓库选择、读取开放 Issue、标签与时间展示、正文预览和人工导入操作。
- 已导入 Issue 禁用重复导入；未配置仓库、非 GitHub 仓库、凭据缺失、网络失败或响应非法时显示稳定错误，不覆盖现有来源。
- Token 从仓库已绑定的 GitHub OAuth Token 或 Personal Access Token 读取，只存在于 Rust 请求和内存中。
- 不提供 Issue 创建、编辑、关闭、评论、分配、自动刷新或后台轮询。
- 不增加 MCP 工具，MCP 总数仍为 11；Agent 不能拉取、选择或导入 Issue。

### 36.4 验收

- 适配器测试覆盖固定查询参数、Pull Request 过滤、50 条上限、正文与标签限长、非法 URL、非法时间和单条 Issue 解析。
- 应用测试覆盖仓库与凭据校验、Issue 转 Markdown、artifact 与来源哈希落库、锚点、重复导入拒绝和 Token 不写入项目目录。
- 前端测试覆盖仓库选择、列表加载、已导入状态、稳定错误和只读说明。
- 全量门禁、安装包、D 盘覆盖安装、11 个 MCP 工具和 SQLite 架构 9 数据保留验收通过。

## 38. 阶段 19：GitHub Project 只读概览

实现状态：已完成（2026-11-13）。详细设计见 `docs/superpowers/specs/2026-11-13-coldstart-github-projects-design.md`。

阶段 19 在“需求导入”页增加 GitHub Projects v2 只读概览，让人工查看已映射仓库关联的项目和有限条目状态，作为外部协作进度的参考。它不把 Project 当作需求来源、计划来源或任务状态源，也不扩大 Agent 权限。

### 38.1 GraphQL 数据映射

- 项目标题、条目标题、字段、节点 ID、链接和时间均经过长度、控制字符、协议与 RFC 3339 校验。
- 项目连接或条目连接达到上限时标记截断；GraphQL errors、缺少 data、仓库不可见或结构非法时整体失败。

### 38.2 应用、界面与权限

- `GitHubProjectService` 复用既有仓库映射与凭据解析；非 GitHub.com、未配置凭据或凭据类型不符时返回 `github_project_ineligible`。

- “需求导入”页提供仓库选择、手动读取、加载态、错误态、空态、项目卡片和条目字段展示。
- 读取失败时清空当前视图，不展示旧快照；切换仓库会清空旧概览与错误。
- OAuth Device Flow 增加 `read:project` scope；PAT 需要 Projects 只读权限。
- 面板明确标注只读，说明不会创建、修改项目、字段或条目，也不会导入需求或蓝图。

### 38.3 安全与边界

- 不写 SQLite、不产生项目事件、不写项目文件、不升级数据库架构。
- 不保存 GraphQL 原始响应、Token、查询正文、评论、Issue 正文或附件。
- Project 概览只存在当前界面内存，不进入 MCP 响应、任务上下文、项目简报或项目记忆。
- 不增加 MCP 工具，MCP 总数仍为 11；Agent 不能读取或修改 Project。
- 不创建 Project、不修改字段或条目、不导入 Project、不同步计划、不后台轮询。

### 38.4 验收

- 适配器测试覆盖 GraphQL 请求、Bearer 头、Token 隔离、5/30/10 上限、截断、条目类型和非法响应。
- 应用测试覆盖仓库与凭据校验、视图映射、读取不新增项目事件、Token 不写入项目目录。
- 前端测试覆盖仓库选择、项目与字段展示、截断提示、错误态和只读说明。
- 全量门禁、生产构建、安装包、D 盘覆盖安装、11 个 MCP 工具和 SQLite 架构 9 数据保留验收通过。

## 39. 阶段 20：多仓库交付总览

实现状态：已完成（2026-11-13）。详细设计见 `docs/superpowers/specs/2026-11-13-coldstart-delivery-overview-design.md`。

阶段 20 在“项目总览”页增加只读的多仓库交付视图，把当前已发布计划中的任务、仓库验证配置、最近 Git 推送、PR/Checks、AI Review 和下一步建议按仓库聚合。它不新增网络请求、写入、数据库迁移或 MCP 工具，也不改变任何任务状态。

### 39.1 聚合来源

- 只读取当前项目已发布计划、工作项与任务契约。
- 只读取已映射仓库、仓库验证命令和最近 Git 同步记录。
- 只读取现有 PR 记录、`pull_request_insights` 快照，以及 PR 对应报告的 AI Review 状态。
- 不调用会同步能力状态的 `IntegrationService::load_workspace`，避免总览读取产生写操作。
- 编码任务没有仓库键或引用未配置仓库时计入“未关联任务”，避免静默遗漏。

### 39.2 仓库视图

- 按 `server`、`admin`、`web`、`app`、`mini_program` 固定顺序展示最多 5 个仓库。
- 展示有效任务完成度，以及可领取、执行中、阻塞、失败、待验收、已重开、草稿和取消计数。
- 展示验证命令数量、最近一次 Git 同步状态与时间、最近 PR 的 Checks、合并冲突、Review 状态和同步时间。
- 同一仓库优先选择最近开放 PR；没有开放 PR 时选择最近创建或更新的 PR 记录。
- 仓库状态分为 `attention`、`active`、`ready`、`complete`、`idle`，风险优先于普通进行中状态。
- 每个仓库只给出一个按风险优先级排序的中文下一步建议。

### 39.3 桌面与安全边界

- 新增 Tauri `load_delivery_overview` 命令；Rust 负责聚合，前端不拼接多个工作区接口。
- 总览读取不写 SQLite、不产生项目事件、不写项目文件、不升级数据库架构。
- 不读取凭据值，不返回 Secret、认证头或远程凭据。
- 不发起 GitHub/Git 网络请求，不后台轮询，不自动刷新。
- 不增加 MCP 工具，MCP 总数仍为 11；交付总览不进入 MCP 响应或任务上下文。
- 不自动领取、合并、关闭、评论、重跑 Checks、部署、打包、提审或发布。

### 39.4 验收

- Rust 单元测试覆盖任务计数、仓库顺序、未关联任务、PR 选择、风险状态和下一步优先级。
- 应用测试覆盖真实 SQLite 接线与读取不新增项目事件。
- 前端测试覆盖成功卡片、空态、仓库入口、错误清空旧快照和只读说明。
- 全量门禁、生产构建、安装包、D 盘覆盖安装、11 个 MCP 工具和 SQLite 架构 9 数据保留验收通过。
